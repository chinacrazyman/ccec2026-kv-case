# 课堂演示脚本

## 一、课程定位

本脚本用于“面向高并发 KV 系统的数据结构工程化教学案例”的课堂演示，可服务于以下课程：

- 数据结构
- 数据结构与算法
- Java 核心编程

案例适合安排为 4 次课，也可压缩为 1 次综合示范课。课堂主线为：

```text
一个高并发 KV 系统从“能跑”走向“可用”的四次工程重构
```

四次重构分别是：

1. 性能重构：从大 O 复杂度走向 CPU Cache 与内存局部性。
2. 安全重构：从平均 `O(1)` 走向极端碰撞防御。
3. 并发重构：从单线程容器走向并发安全容器。
4. 容量重构：从精确集合走向概率型数据结构。

---

## 二、总体课堂目标

通过本案例，学生应能够：

1. 解释时间复杂度与真实运行性能之间的差异。
2. 说明 HashMap 在极端碰撞下的复杂度退化过程。
3. 分析普通 HashMap 在多线程共享写入下的数据丢失风险。
4. 比较 Hashtable 与 ConcurrentHashMap 的同步策略差异。
5. 推导 Bloom Filter 的空间占用与误判率关系。
6. 形成“数据结构选择必须服从工程约束”的系统思维。

## 五、课堂导入脚本

### 教师开场

同学们，前面我们学习了数组、链表、树、哈希表等数据结构。传统学习中，我们通常关心一个问题：它的时间复杂度是多少？例如 HashMap 查询通常是 `O(1)`，红黑树查询是 `O(log n)`，双重循环是 `O(n²)`。

但是，真实工程系统并不会因为我们在纸上写对了复杂度就自动高性能、自动安全、自动稳定。今天我们换一个角度来看数据结构：如果把它放进一个高并发 KV 系统中，它会遇到什么问题？

这里的 KV 指 Key-Value，也就是键值对。Redis、Memcached、缓存系统、会话系统、商品 ID 查询系统，本质上都在做一件事：根据 Key 快速找到 Value。

今天我们通过四个实验，观察一个高并发 KV 系统要跨过的四道工程边界：性能边界、安全边界、并发边界和容量边界。

## 六、案例一脚本：CPU Cache 与内存访问局部性

### 1. 导入提问

教师提问：

如果两段代码都是双重循环，循环次数完全一样，时间复杂度也都是 `O(n²)`，它们的运行速度一定差不多吗？

预期学生回答：

大多数学生会认为差不多，最多只是常数差异。

教师回应：

下面我们不先讲理论，直接运行代码。

### 2. 运行代码

运行类：

```text
CacheLineLiveDemo
```

展示控制台输出：

- 按行优先遍历耗时。
- 按列优先遍历耗时。

### 3. 课堂追问

教师提问：

1. 两段代码循环次数是否一样？
2. 时间复杂度是否一样？
3. 为什么耗时差异这么大？
4. 是不是大 O 符号“错了”？

引导学生回答：

大 O 没有错，但它描述的是增长趋势，不等于真实机器上的完整性能模型。

### 4. 原理解释

教师讲解要点：

- Java 的 `int[][]` 本质是数组的数组。
- 每一行 `int[]` 内部有连续访问特征。
- CPU 读取内存时通常按 Cache Line 读取。
- 一个常见 Cache Line 为 64B，一个 `int` 为 4B，因此一次可能带入 16 个相邻整数。
- 按行访问更符合空间局部性。
- 按列访问频繁跨行，容易导致 Cache Miss 和内存访问延迟。

### 5. 教学总结

教师总结：

这一实验说明，数据结构教学不能只停留在纸面复杂度。真实工程性能还受到 CPU Cache、内存布局、预取机制和访问模式影响。复杂度分析是必要的，但不是全部。

## 七、案例二脚本：HashMap 极端碰撞与 Hash DoS 防御

### 1. 导入提问

教师提问：

我们常说 HashMap 查询是 `O(1)`。那么，它在任何情况下都是 `O(1)` 吗？

学生可能回答：

如果哈希冲突很多，可能会退化。

教师继续追问：

如果有人故意构造大量哈希冲突数据，会发生什么？这只是考试里的最坏情况，还是生产系统中的安全风险？

### 2. 运行代码

运行类：

```text
HashDoSAttackDemo
```

展示三个阶段：

1. `"Aa"` 和 `"BB"` 的 hashCode 完全相同。
2. 生成 65536 个哈希值完全一致的字符串。
3. 对比传统链表 HashMap 和 Java 8 HashMap 的耗时。

### 3. 课堂追问

教师提问：

1. 为什么不同字符串会有相同哈希值？
2. 如果所有 Key 都落到同一个桶中，HashMap 还快吗？
3. 为什么传统链表 HashMap 会非常慢？
4. Java 8 为什么要把链表转成红黑树？
5. 红黑树是不是为了“考试好看”才引入的？

### 4. 原理解释

教师讲解要点：

- 哈希函数不是一一映射，碰撞不可避免。
- 平均情况下，HashMap 查询接近 `O(1)`。
- 极端碰撞时，桶内链表变长，查询和插入可能退化为 `O(N)`。
- 如果连续插入大量碰撞 Key，总体耗时可能接近 `O(N²)`。
- Java 8 引入树化机制，在特定条件下将链表转为红黑树，将复杂度控制在 `O(log N)`。
- 红黑树在这里不是孤立知识点，而是极端场景下的安全兜底结构。

### 5. 教学总结

教师总结：

这一实验说明，平均复杂度不代表系统永远安全。数据结构设计不仅影响性能，也可能关系到系统抗攻击能力。工业级数据结构必须考虑极端输入和防御性设计。

## 八、案例三脚本：并发写入与并发容器工程权衡

### 1. 导入提问

教师提问：

如果一个 HashMap 在单线程下运行正常，能不能直接放到 Web 服务器中，让多个请求线程同时写入？

学生可能回答：

不可以，需要考虑线程安全。

教师继续追问：

如果 Key 都不重复，HashMap 还会丢数据吗？

### 2. 运行代码

运行类：

```text
ConcurrencyCrashTest
```

展示实验参数：

- 并发线程数。
- 每线程写入数据量。
- 理论预期总数据量。

展示三类容器：

1. 普通 HashMap。
2. Hashtable。
3. ConcurrentHashMap。

### 3. 课堂追问

教师提问：

1. 本实验中的 Key 是否重复？
2. 如果 Key 不重复，但最终 size 变小，说明什么？
3. 普通 HashMap 为什么会丢数据？
4. Hashtable 为什么能保证数据完整？
5. ConcurrentHashMap 与 Hashtable 的同步策略有何不同？
6. 为什么不能简单地说 ConcurrentHashMap 在任何情况下都一定最快？

### 4. 原理解释

教师讲解要点：

- 普通 HashMap 没有同步保护。
- 多线程同时修改内部结构时，可能出现覆盖、丢失或结构异常。
- Hashtable 通过方法级 `synchronized` 保证线程安全，但同步粒度较粗。
- ConcurrentHashMap 使用 CAS、桶级同步等机制，提高并发扩展能力。
- 在短时纯写入测试中，ConcurrentHashMap 不一定每次都比 Hashtable 快。
- 真正要理解的是：线程安全、锁粒度、实现复杂度和并发扩展性之间的权衡。

### 5. 教学总结

教师总结：

这一实验说明，数据结构进入并发环境后，问题不再只是“查得快不快”，还包括“数据是否可靠”。线程安全是生产系统的底线，而并发容器的设计体现了安全性与扩展性之间的平衡。

## 九、案例四脚本：Bloom Filter 海量数据判重

### 1. 导入提问

教师提问：

如果要判断 10 亿个商品 ID 是否存在，你会用什么数据结构？

学生可能回答：

HashSet 或 HashMap。

教师继续追问：

如果每个对象都有对象头、引用、节点开销，10 亿个 ID 会占用多少内存？服务器是否承受得住？

### 2. 运行代码

运行类：

```text
BloomFilterLimitDemo
```

展示内容：

1. 理论容量规划。
2. 写入 1000 万合法商品 ID。
3. 查询合法 ID。
4. 模拟 100 万非法 ID 请求，统计误判率。

### 3. 课堂追问

教师提问：

1. 布隆过滤器为什么能节省空间？
2. 为什么它不会把已加入的数据误判为不存在？
3. 为什么它可能把未加入的数据误判为“可能存在”？
4. 在缓存穿透场景中，误判放行意味着什么？
5. 为什么工程系统愿意接受极小概率的误判？

### 4. 原理解释

教师讲解要点：

- 布隆过滤器使用位数组和多个哈希函数。
- 插入元素时，将多个哈希位置置为 1。
- 查询元素时，如果任意位置为 0，则一定不存在。
- 如果所有位置均为 1，则只能说明可能存在。
- 误判率可以通过位数组长度和哈希函数个数进行控制。
- 它体现的是用可控误判率换取巨大的空间节省。

### 5. 教学总结

教师总结：

这一实验说明，在海量数据场景中，绝对精确并不总是最优方案。工程系统常常需要在空间、时间和准确率之间做权衡。布隆过滤器的价值，不在于完美，而在于可控的不完美。

## 十、综合总结脚本

教师总结：

今天我们通过四个实验重新认识了数据结构。

第一个实验告诉我们，相同时间复杂度不代表相同真实性能，硬件和内存访问模式会影响程序速度。

第二个实验告诉我们，平均复杂度不代表极端输入下的安全性，HashMap 也可能成为攻击目标。

第三个实验告诉我们，单线程正确不代表多线程可靠，线程安全和锁粒度是工程系统必须面对的问题。

第四个实验告诉我们，海量数据场景下，精确结构可能被物理内存击穿，概率型结构可以通过可控误判换取空间优势。

所以，数据结构不是只存在于教材中的图和公式，而是支撑真实系统性能、安全、并发和容量的底层基础。真正的工程能力，不是记住某一种结构最好，而是能够在具体约束下做出合理选择。

## 十一、板书或 PPT 主线建议

```text
实验冲突 → 原理解释 → 源码验证 → 架构权衡 → 学习产出
```

四个模块分别对应：

| 模块 | 实验冲突 | 工程结论 |
|---|---|---|
| CPU Cache | 同样 O(n²)，耗时差异巨大 | 复杂度不是完整性能模型 |
| Hash DoS | O(1) 哈希表被碰撞拖垮 | 极端输入需要防御性设计 |
| 并发容器 | Key 不重复仍然丢数据 | 单线程正确不代表并发可靠 |
| Bloom Filter | 精确集合内存代价过高 | 可控误判换取空间优势 |
